# proxy-forge: high-level spec (draft)

Working name. A local web app that turns a Magic: The Gathering deck list into printable proxy cards with custom generated art. Single user, personal use only (not for sale or distribution).

## Goal

1. Paste or upload a deck list.
2. Pick a card template and a style profile.
3. Get print-ready proxies (PNG per card, plus PDF print sheets) with art generated by the studio's image model, tailored by reference photos and verbal direction.

## Where it runs

- Own repo: `D:\proxy-forge`, GitHub `hunter13118/proxy-forge`. Python (FastAPI) backend, plain HTML/JS frontend, no build step.
- Runs on the studio PC, port TBD, behind its **own named tunnel and hostname**, the same way the studio is set up. Other tunnels stay untouched.
- Gate it with the same Clerk allowlist mechanism the studio uses, so it is not public.
- Data and images live on G: (NVMe), never C:. Bulk Scryfall data goes there too.

## Core flow

1. **Deck import.** Parse a text deck list (the common "1 Card Name (SET) 123" export format). Each card is resolved against Scryfall.
2. **Card data.** Use the Scryfall bulk `default_cards` file on G: for lookups (no per-card hits in a batch). Fall back to `/cards/named?fuzzy=` for misses. Send a User-Agent and Accept header, keep 50-100 ms between requests, cache everything.
3. **Prompt.** For each card, build a prompt from its type line, colors, and an art description derived from the oracle text. Add the **style profile** (below). Keep it text-only: never feed Scryfall's existing art in as a reference.
4. **Generate.** Submit one ComfyUI job per card (Anima-Turbo by default), at the card's art aspect ratio. Cache by `(card id, style profile hash, seed)`, so reruns skip finished cards.
5. **Compose.** Render the frame, name, mana cost, type line, rules text, and P/T over the generated art using a chosen template. Output a PNG per card at 2.5 x 3.5 in / 300 DPI, plus a PDF of 3x3 print sheets.

## Style profile (where "influence" lives)

A saved profile holds:

- **Verbal direction:** free text, for example "warm watercolor, the cast look like my friends, leaning on sunset tones". Turned into prompt fragments by the local LLM.
- **Reference photos:** a few images of people the user wants in the art. Stored locally (on G:, never committed).
- **Optional LoRA:** a trained adapter for a person or a look, if the profile needs consistency across many cards.
- **Template:** the frame and layout to use.

Attaching a person to a card should be explicit: the user picks which profile subject a card should feature (for example, the legendary creature or the protagonist), and the app does not guess.

### Reference method (open question, decide by testing)

- **Option A: reference conditioning.** Checked against the studio: ComfyUI has no custom nodes installed, and the studio's own notes say Anima has no image-prompt adapter ("who is who comes from the words and, later, a LoRA"), while IP-Adapter refs hurt Animagine and wreck NoobAI. So true image conditioning would mean new downloads and is not built. What is built instead is the no-download equivalent: a local vision model (qwen3-vl) turns each person's photos into appearance tags plus a sentence, shown on the page for editing, and those words go into every prompt the person is assigned to. Likeness is approximate (hair, glasses, build), not a face match.
- **Option B: per-person LoRA** with the existing trainer (`G:\anima_lora`). Better likeness and consistency across 60+ cards. Costs about 15-30 photos and a training run per person. Profiles already carry a `lora` field and the page can pick any LoRA ComfyUI knows, so a trained person-LoRA drops in.
- Decision (2026-11-02): build A as described above, measure likeness on real photos, and move to B for anyone it is not good enough for.

## Acceptance (v1)

- A 60-card deck completes end to end on the 5090 in a time we record during M2. The target is a few hours or less. Reruns hit the cache.
- Every card's art is generated with the chosen profile, and the chosen subjects appear in the cards they were assigned to.
- Output prints at the correct card size.
- The app is reachable only through its own tunnel, behind the allowlist.

## Constraints

- One GPU: jobs run serially through the queue, with `make_room` before generation and nothing else heavy running.
- Displays take about 6 GB of VRAM when on (memory notes), so the generation guard must account for them.
- Never install or cache on C:.
- Friends' photos are personal data: stored only on G:, never committed to git, never sent off the machine.
- Personal use only. The Anima licence is non-commercial, and Scryfall and Wizards' IP do not permit selling proxies.

## Update (2026-11-03): the studio is a service

M0 went further than a shared package. The studio now serves the models to other apps through its own API (`ebook-av-service/docs/AI-API.md`, routes `/v1/ai/*`: words, pictures, LoRA training),
and proxy-forge consumes it (`proxy_forge/studio.py`) instead of talking to ComfyUI, Ollama and the trainer itself. The studio keeps the GPU, the models and the trainer; proxy-forge keeps cards,
prompts, templates, profiles and people. The table above is the history; what each need uses now:

| Need | Now |
|---|---|
| Prompt writing, photo description | `POST /v1/ai/text` (language model, or the vision model when pictures are sent) |
| Art | `POST /v1/ai/images` (a job; style LoRA first, people LoRAs after, optional restyle pass for the cartoon look) |
| Person LoRAs | `PUT /v1/ai/datasets/..` then `POST /v1/ai/lora-trainings` (the studio deletes the photos when the run ends) |
| GPU sharing | the studio (one worker, its picture lock, `make_room`) |
| Sign-in | still `studio-kit` (`web_auth`, `clerk_auth`) |
